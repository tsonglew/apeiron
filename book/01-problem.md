# 01. 问题：为什么需要 harness

2026-08-26

## Agent = Model + Harness

DeepSeek Harness（dsh）官方表述是：**Agent = Model + Harness**——模型负责「想」，
harness 负责「执行」：文件读写、shell、工具调用、计划、长任务运行。

这个表述在 2026 年成立，因为模型普遍具备 tool-calling 之后，缺口已经不在推理能力，
而在**把推理接进真实世界的执行基础设施**。benchmark 排名第一和「能不能干活」
是两件事：同样的模型，换一个 harness，成绩和行为都会大变（dsh 官方承认部分
V4-Pro 得分是在自己 harness 里测的，不是纯模型数字）。

结论：harness 是自己有分量的工程问题，值得专门做。

## 状态：被低估的核心

初版设计直觉上会把 harness 当成「模型调用循环 + 工具注册表」。
但真正让一堆 demo 变成可用产品的，是**会话状态**。四个场景都指向它：

1. **恢复**：进程崩溃 / 断连 / 长任务杀进程——状态在，就能续跑；
2. **分叉与回滚**：评测、调试「如果上次换个思路会怎样」——需要树上可回放的历史；
3. **子代理**：子任务挂到父任务上，可观测、可归并——需要树结构；
4. **实时介入**：steer（中途插话）、abort、审批——需要对齐「当前会话写到哪了」。

而当我们想要「状态可用」的工程保证时（多机、多进程、崩溃恢复），
就得到本题的题眼：**分布式状态存储**。

## 2026-08 时点的现状：**没有人把分布式做好**

- **pi**（earendil-works/pi，前身 pi-mono）：三层的持久化是本地文件/SQLite，
  会话树、save point 都很好，但存储绑定单进程；
- **Codex Harness**（openai/codex）：Rust 核心，`thread-store` 持久化会话，
  协议（app-server）是全行业最好的，存储同样是本地单进程；
- **DeepSeek Harness**：`Everything is a Plugin`，存储是插件槽之一，
  trace-first 设计理念最到位，但核心（rc.5→rc.8 一周连跳）未稳，
  分布式语义要靠社区插件补。

三家各自贡献了拼图的不同块（详见下章），**分布式状态存储这块拼图是空白的**。
apeiron 的目标，就是把这块补上，同时吸收三家的全部优点。

## 我们的目标定义

> 面向**有状态**智能体（含**分布式状态存储**）的 agent harness。

一句话方案：会话是**不可变事件日志**（单一源真），任何进程都可以恢复；
每会话**单写者**，把分布式正确性压缩到「一个约束」。
