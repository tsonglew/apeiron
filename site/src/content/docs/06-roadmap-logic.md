# 06. 路线图为什么这样排

2026-08-26。与 [ROADMAP.md](../ROADMAP.md) 配对：那边是计划，这里是计划背后的推理。

## 大方向：基础 → 复杂

M0 单进程骨架 → M1 单机完整闭环 → M2 分布式状态 → M3 规模与评测 → M4 生态。
不是「功能枚举」的顺序，而是**依赖关系的顺序**：

- 状态模型不成立，分布式无从谈起（M0 必须先于 M2）；
- 协议不定，host/评测/互操作全是返工（M0 必须立协议）；
- trace 不复现，分布式恢复无法验证（M1 必须接评测）；
- 单机闭环不好用，分布式只是加了慢（M1 必须先于 M2 的「打磨」）。

## 四条具体的排序判断

### 1. 协议先行（M0 而非 M1）

协议（Thread/Turn/Item + JSON-RPC）是所有 host、评测、外部互操作的契约。
Codex 的证明：open-sourcing 的点是 app-server 协议而不是代码库本身。
**协议后改 = 换合同，成本随宿主数量线性增长**，M0 定下来最便宜。

### 2. compaction 排在分布式恢复之前（M2 内部顺序）

分布式恢复 = snapshot + tail 重放。如果日志无限增长，
每次接管都全量重放 = 恢复时间随会话长度线性恶化，甚至不可用。
所以理解上：**compaction 不是「优化」，是「让恢复语义存在」的前提**。
M1 做 v1（超阈生成 SUMMARY），M2 恢复直接用它的 last_boundary。

### 3. 评测 M1 就接线，而不是发布会前

trace 有两种消费者：人和程序。headless 四指标（turns/token/耗时/成本）
在 M1 的钱很小，在 M3 带来「run-to-run 对比→行为回归检测→模型升级验证」。
**没有 trace 就没有「崩溃恢复后行为一致」的测试手段**——
分布式语义的验证本身是个评测问题，不是运维问题。

### 4. 权限审批放 M1 而非 M0

pi 的教训是「没有内建权限系统」被点名，但 M0 阶段 harness 连真实工具都没有，
审批流无对象可审。放在 M1：与 bash/fs 工具**同一批落地**（工具 + 审批一起交付），
避免「功能先跑、安全后补」变成临时的永久（著名的「临时变永久」问题）。

## 明确不做的事

- **不做 CRDT**：单写者 + seq 已经把并发消灭，CRDT 是给多写者语义的问题付复杂度；
- **不做多租户计费**（M4 再议）：框架阶段无人可计费，先保证核心正确；
- **不照搬 dsh 的「一周 5k 插件」路线**：生态爆发的前提是核心稳定 + 协议冻结，
  这正是 dsh 的教训（rc 连跳、零 issue 策略）。apeiron 先立
  semver 纪律 / payload 版本化 / 协议冻结，再谈生态。

## 风险与证伪

- **最大的风险是「分布式真的有人用吗」** ⚠️：M2 前必须用真实场景
  （长任务 + 崩溃 + 接管）验证，否则 M2 是在做没有用户的功能——所以
  M1 的验收里含有「真实任务跑通」，M2 的每一步都以「kill -9 后恢复」为证伪点；
- **次大风险是评测模型**：`messages_from_log` 的线性重建在 M2 的多 lane /
  并行子代理下需要扩展——⚠️ 需要在 M1 的子代理 v1 里先验证树的读取，
  而不是等到 M2 才发现投影层不懂树。
